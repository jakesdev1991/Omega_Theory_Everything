# Software supply-chain and dependency-readiness controls

**Status date:** 2026-10-15

**Purpose:** make dependency and automation evidence reviewable before a testnet or
value-bearing decision. This document is not a security audit, legal opinion, license
determination, deployment approval, or assurance that a component is safe.

## What is checked in the repository

| Control | Evidence | Current role |
|---|---|---|
| Source-and-lockfile inventory | [`sbom/omega-theory-everything.cdx.json`](sbom/omega-theory-everything.cdx.json), generated by [`../tools/generate_dependency_inventory.py`](../tools/generate_dependency_inventory.py) | Records declared Python/MCP dependencies, committed npm lockfile components, local Cargo manifests, Lean pins, GitHub Actions, and the vendored ethers bundle. |
| Inventory freshness | `python tools/generate_dependency_inventory.py --check` | Fails when a supported manifest/lock/workflow/vendor input changes without regenerating the inventory. It is included in the local consistency gate and Python tests. |
| Production npm advisories | `node tools/audit_npm_production.mjs` | Runs `npm audit --omit=dev --package-lock-only --audit-level=high` for every committed npm workspace. CI fails on high/critical production findings. |
| Development npm exception ratchet | `node tools/audit_npm_development.mjs`, [`security/npm-development-audit-exceptions.json`](security/npm-development-audit-exceptions.json) | Full-tree audit that permits only the reviewed, time-bounded web lint-chain exception. A new advisory, changed path, expired review, or stale exception fails CI. |
| Python resolver advisory gate | `pip-audit -r requirements.txt --strict`; `pip-audit mcp --strict` | CI resolves the root requirements and the separate MCP project under its Python 3.12 job, then fails on known advisories or an unauditable dependency. Both projects use version ranges, so this is a live resolver check rather than a fully pinned Python lockfile. |
| Dependabot configuration coverage | `python tools/check_dependabot_coverage.py`, [`.github/dependabot.yml`](../.github/dependabot.yml) | Derives expected GitHub Actions, pip, npm, and top-level Cargo project coverage and rejects a missing/stale project, duplicate stanza, nonweekly schedule, or zero PR limit. |
| Filesystem / secret scans | `.github/workflows/ci.yml` | Trivy scans the checkout and TruffleHog scans relevant history; both are useful controls, not a replacement for reviewed alert queues. |
| GitHub Action pinning | `tests/test_workflow_policy.py` | Every third-party `uses:` reference in shipped workflows must use a full commit SHA. This avoids a tag moving underneath a previously reviewed workflow. |

## Reproducible inventory

Generate or check the committed inventory from the repository root:

```bash
python tools/generate_dependency_inventory.py
python tools/generate_dependency_inventory.py --check
```

The generated document uses CycloneDX 1.5-shaped JSON for interoperability, but the
name **source-and-lockfile inventory** is intentional. It is not a complete production SBOM.
In particular, it does **not** establish:

- the license, provenance, acceptability, or redistribution rights of every component;
- a resolved lock for Python requirements expressed as ranges;
- operating-system packages, container/base-image packages, compiler downloads, runtime plugins,
  deployed infrastructure, private operator dependencies, or browser-delivered third-party content;
- the provenance or safety of an artifact after it leaves the reviewed source tree.

Any release reviewer must add those sources and record license/security decisions in an
access-controlled evidence register. Do not put keys, private deployment manifests, personal
contacts, or confidential legal material into the public inventory.

## Production npm advisory gate

Run this command locally or let CI run it after the web build:

```bash
node tools/audit_npm_production.mjs
```

It reads lockfiles only, does not run lifecycle scripts, and evaluates production dependency trees
for `amity`, `desktop`, `evm`, `mobile-node`, `nostr-client`, `solana`, and `web`. It intentionally
uses `--omit=dev`: a developer tool is not part of a shipped browser/server/desktop runtime.
That scope is a boundary, **not** an assertion that development dependencies are risk-free.

### 2026-10-15 remediation record

The initial production-only audit found high-severity advisories in the web lockfile through
`next@16.3.6`, `sharp@0.35.4`, and `source-map-js@1.2.1`. The lockfile was updated and tested with:

- `next` and `eslint-config-next` at `16.4.1`;
- the patched transitive `sharp@0.35.5`;
- the patched transitive `source-map-js@1.2.2`.

After that update, the production-only audit reported **0 high/critical findings** across every
committed npm workspace. The web typecheck, 33 domain tests, production build (54 routes), and
production npm audit all passed on the updated lockfile.

A full audit that includes developer-only packages still reports a high-severity chain through
`@next/eslint-plugin-next` → `fast-glob` → `micromatch` → `braces@3.0.3`
([GHSA-vfj7-8cjw-p6xm](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm)). At the time of this
record, `braces@3.0.3` is the latest published 3.x release and `@next/eslint-plugin-next@16.4.1`
uses `fast-glob@3.3.1`; npm offers only an incompatible downgrade as its automated fix.

This is a **development-tooling risk**, not a silent suppression or a production-zero security
proof. CI runs `node tools/audit_npm_development.mjs`, which reads the public exception register
and invokes `npm audit --package-lock-only --json` without running lifecycle scripts. It fails if
the advisory changes, another package/advisory appears, the dependency path changes, the exception
becomes stale, or its `review_by` date passes. The current exception must be
reassessed by **2026-11-15**; removing it after an upstream remediation is the expected outcome.
It cannot be accepted as evidence for a value-bearing launch.

## Python resolver audit and Dependabot maintenance coverage

The root Python CI job installs the pinned audit tool from `requirements.txt` and runs:

```bash
pip-audit -r requirements.txt --strict
```

The separate MCP job uses its declared Python 3.12 environment and runs:

```bash
pip-audit mcp --strict
```

The root command resolved 51 packages with zero known vulnerabilities on 2026-10-15; a local
`pip-audit mcp --strict` resolution also found no known vulnerabilities. CI repeats the MCP audit
under Python 3.12. Both are live advisory checks: the scientific runtime and MCP dependencies use
version ranges and do not yet have committed resolver lockfiles. Thus a green result means the
current resolver found no known advisory, not that every future resolution or deployed Python
environment has been reviewed.

Dependabot is configured weekly for GitHub Actions, the root and MCP Python projects, every
discovered npm lockfile, the Rust workspace, and the independent desktop Tauri Cargo project.
Validate that coverage locally with:

```bash
python tools/check_dependabot_coverage.py
```

The checker derives the required set from the checkout and fails if an eligible project is not
configured. It validates configuration only; it neither enables Dependabot alerts nor proves that
pull requests or alerts receive human review.

## GitHub alert visibility is still a blocker

On 2026-10-15, the GitHub REST API reported that **Dependabot alerts are disabled** for this
repository. This workspace also did not have permission to read Code Scanning or Secret Scanning
alert state. A successful CI scan cannot tell a release owner whether alerts are enabled, retained,
dismissed with rationale, or assigned to a reviewer.

Before a public testnet pilot, a repository administrator should:

1. enable Dependabot alerts and confirm alert access for a named security reviewer;
2. verify Code Scanning and Secret Scanning are enabled, visible, and retained appropriately;
3. set a severity/response SLA and an escalation route;
4. export or otherwise retain the first reviewed alert state in a private evidence register;
5. document all accepted residual risks and their expiry/review date.

## Relationship to release readiness

[`../launch/readiness-gates.json`](../launch/readiness-gates.json) is the canonical public
blocker ledger. The inventory and audit controls advance only narrow technical sub-gates; they do
not complete provenance, independent security review, operator incident ownership, legal/compliance
review, testnet drills, or the C.A.R.E. mainnet safety gate.

Use the checker to distinguish a valid ledger from a genuinely unblocked launch scope:

```bash
python launch/check_readiness.py --validate
python launch/check_readiness.py --report --scope testnet-pilot
python launch/check_readiness.py --require mainnet  # correctly exits non-zero today
```
